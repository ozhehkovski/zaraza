# Развёртывание на сервере

Нужен Linux-сервер с Docker Engine и Docker Compose v2, поддерживающим `up --wait`. Начальная конфигурация для 20 товаров: 2 vCPU, 4 GB RAM и свободное место для Docker/базы/backup. Это стартовая оценка по локальному расходу Chromium около 1,7 GB, не гарантия работы с 200 реальными товарами. Исходящие HTTPS-запросы к Telegram и Zara должны быть доступны. Входящие порты открывать не требуется: бот использует long polling, health доступен на localhost:8080.

## Первый запуск

Распакуйте архив исходников в отдельную папку проекта. Он не содержит токен, `.env`, базу и node_modules. Затем:

```sh
cp .env.example .env
chmod 600 .env
openssl rand -hex 24
# В редакторе впишите результат в POSTGRES_PASSWORD,
# а токен бота — в TELEGRAM_BOT_TOKEN.
./scripts/deploy.sh
curl -f http://localhost:8080/health
docker compose logs --tail=50 app
```

На сервере используйте только `docker-compose.yml`; dev override открывает порт базы для локальной разработки. Chromium и Xvfb уже входят в образ. Рекомендуемая конфигурация Zara задана в `.env.example`: browser + page, headless=false, две страницы. Cookies не требовались для локальной проверки.

Если переносите тот же бот, остановите локальный app **до запуска app на сервере** (`docker compose stop app`). Telegram long polling с одним токеном должен работать в одном месте. Без восстановления backup сервер начнёт с пустой базой: нажмите Start и добавьте товар в боте. Пока нет товаров, `zara.status=unchecked` допустим; после добавления нужны реальные успешные проверки.

Если build успешен, но скрипт завершается ошибкой ожидания healthy, контейнеры остаются доступными для диагностики. Проверьте логи и `/health`. Не перезапускайте контейнер бесконечно при блокировке магазина.

## Перенос существующих подписок

На текущем компьютере остановите только app и создайте свежий backup:

```sh
docker compose stop app
./scripts/backup.sh
```

Скопируйте `.dump` на сервер отдельно от исходников и сохраняйте с правами 600: база содержит Telegram ID и подписки. На сервере с новой пустой базой и заполненной `.env`:

```sh
docker compose up -d --wait postgres
docker compose exec -T postgres pg_restore -U tracker -d tracker --exit-on-error < /path/to/tracker.dump
./scripts/deploy.sh
```

Эта процедура предназначена только для новой пустой базы. Не восстанавливайте dump поверх работающей базы. Миграции при старте применят совместимые дополнения автоматически. Имена проекта/папки определяют имя Docker volume: сохраняйте их при обновлениях. Не используйте `docker compose down -v`.

## Backup и обновления

```sh
./scripts/backup.sh
# обновите исходники в той же папке, сохранив .env
./scripts/deploy.sh
```

Backup использует `pg_dump -Fc`; восстановление проверено в отдельной тестовой БД, все 20 подписок сохранились. Каталог по умолчанию `backups/`, можно задать `BACKUP_DIR`. Удалённое хранение и расписание backup настройте на сервере; они не создаются этим проектом автоматически. Восстановление рабочей базы выполняйте в новую БД/volume после остановки app. Пароль существующего PostgreSQL не меняется простым редактированием `.env`: для действующего volume нужна отдельная смена роли PostgreSQL.

## Контроль после запуска

Отправьте настоящую ссылку Zara PL, выберите размер и правило. Проверьте `product checked` в логах, свежий `/list`, `/history`, сохранение подписок после `docker compose restart app`. Проверьте работу на IP сервера в течение суток; успешный локальный тест не подтверждает доступность Zara с другого IP.

`/health` возвращает 503 при ошибке магазина, неизвестном отслеживаемом SKU, проблемах БД или остановке polling/monitor. Docker restart policy восстанавливает завершившийся процесс, но не перезапускает контейнер просто из-за `unhealthy`. Настройте внешнюю проверку health и оповещение об устойчивой ошибке. Короткие таймауты допускают retry/backoff; долго не обновляющиеся подписки требуют разбора.

Логи обоих сервисов ограничены пятью файлами по 10 MB и сжимаются local logging driver. Настройка соответствует [документации Docker](https://docs.docker.com/engine/logging/drivers/local/). Для длительного аудита сохраняйте нужные логи отдельно.

## Проверенный фикс SKU

Zara может переставлять основной `sizes[].sku` и связанные `twinnedSkus`. Подписки и история сохраняются через явные связи этих SKU в рамках товара и одинакового размера. Существующие связанные варианты получают свежие состояния; в выборе размера отображается один вариант. Несвязанный или неоднозначный SKU не заменяется автоматически и не вызывает вымышленный restock.
